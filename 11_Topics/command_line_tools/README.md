# Command-line tools

**One line:** `grep`, `sed` and `awk` are POSIX engines — leftmost-*longest*, no lazy quantifiers, no lookaround, BRE by default — and the same pattern typed into a shell and into a program means something different three times over: the syntax family, the match rule, and the quoting the shell does before the tool ever sees it.

**Level:** 201 · you are about to type a pattern after `grep`

## Three flavours in three flags

| Flag | Flavour | `(` `+` `?` `{` `\|` mean | Has |
| --- | --- | --- | --- |
| `grep`, `sed` (default) | BRE — basic | literals; the operators are `\(` `\+` `\?` `\{` `\|` | `\1` backreferences (required by POSIX in BRE) |
| `grep -E`, `sed -E`, `awk`, `egrep` | ERE — extended | operators, as in every language | backreferences only as a common extension |
| `grep -P`, `pcre2grep` | PCRE2 | as in Perl | everything on the [Keywords](../../10_Keywords/README.md) shelf — lookaround, `\K`, `\d`, lazy quantifiers |

BRE's inverted escaping is the first thing that bites: `a+` in `grep` is a literal `a+`, and `a\+` is one-or-more. ERE is close enough to the language engines to be pasted from them — until the match rule differs.

A badly ordered alternation — `[0-9]+|[0-9]+\.[0-9]+`, integer first — comes back **right** from `grep -o`, `sed` and `awk`, because POSIX takes the longest alternative. Every language engine takes the first and returns `3`. A pattern that works on the command line can therefore be wrong in the program it is pasted into, and the tool will not have warned.

## The three things that differ

1. **Match rule.** Leftmost-longest. [Two definitions of "the match"](../../08_Match_Semantics/leftmost_first_vs_leftmost_longest/README.md) has the C program and the two libcs that disagree about submatches.
2. **No lazy quantifiers.** `a+?` in ERE is `(a+)?`. GNU `grep -E` and `sed -E` and both awks read `<.+?>` as `(<.+>)?` and take the whole line; macOS BSD `grep` is lazy; macOS BSD `sed` refuses. [Greedy and lazy](../../08_Match_Semantics/greedy_and_lazy/README.md) has the six runs.
3. **The shell gets the pattern first.** Inside double quotes, `$` and `` ` `` and `\` are the shell's; inside single quotes nothing is. `\d` is not POSIX — `[[:digit:]]` or `[0-9]` — and `grep -P` is the only `grep` that understands it.

## GNU and BSD

The Mac ships BSD tools; Linux ships GNU. They agree on POSIX and disagree past it: `grep -o` and `-P` are GNU extensions BSD grep partly has, `sed -i` takes an argument on BSD and not on GNU, `sed -E` works on both but `\+` in BRE is GNU-only, and BSD `sed` refuses `a+?`. A shell script that must run on both stays inside POSIX ERE and uses `[[:class:]]` names, or calls `perl -pe`, which is the same everywhere.

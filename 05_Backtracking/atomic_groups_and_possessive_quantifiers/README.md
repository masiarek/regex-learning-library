# Atomic groups and possessive quantifiers — having matched this, never give it back

**One line:** `(?>a+)` and `a++` are one instruction in two spellings — *throw away the backtracking positions inside* — and they change **what a pattern matches**, not only how long it takes to fail.

**Level:** 301 · you have a pattern that is too slow, or one that quietly stopped matching after somebody made it faster

**Keywords on this page:** [`(?>…)`](../../10_Keywords/atomic_group/README.md) · [`*+`](../../10_Keywords/possessive_quantifier/README.md) · [`(?=…)`](../../10_Keywords/lookahead/README.md) · [`\1`](../../10_Keywords/backreference/README.md) — **Topics:** [Performance](../../11_Topics/performance/README.md)

Almost every page about these two constructs sells them as a performance feature and stops there. The half that gets left out is the half that files bugs: `a+a` matches `aa`, and `a++a` matches nothing at all, in any subject, ever.

## What the engine actually discards

A greedy quantifier does two things. It takes as much as it can, and — this is the part that is easy to forget — it **writes down every shorter length it could have taken instead**. Those saved positions are what "backtracking" comes back to.

```text
subject   a a
pattern   a + a

a+ takes "aa", leaving nothing for the final a  -> fail
      backtrack to the position a+ wrote down
a+ takes "a",  leaving "a" for the final a      -> match
```

An atomic group runs the pattern inside it normally, and then, the moment the group has matched, **deletes those saved positions**. Nothing later in the pattern can ask the group to try a shorter length; if the rest of the pattern fails, the whole attempt fails and the match restarts at the next starting position.

A possessive quantifier is the same instruction with a narrower scope, and the equivalence is exact:

| Possessive | Atomic group |
| --- | --- |
| `a++` | `(?>a+)` |
| `a*+` | `(?>a*)` |
| `a?+` | `(?>a?)` |
| `a{2,5}+` | `(?>a{2,5})` |

Block 2 is the equivalence claim, checked rather than asserted: `(?>a+)b` and `a++b` return the same verdict on all eight subjects, including the empty one.

Block 1 is the trap in miniature. `a+a` matches `aa` because the `+` hands a character back. `a++a` has nothing to hand back, so it fails — and it fails at *every* starting position, which makes it a pattern that cannot match any string whatsoever. The engine does not warn you about that. Neither does any engine below.

## The optimisation that silently stops matching

Here is the shape that reaches production. Somebody has a hostname check:

```text
^[\w.]+\.com$
```

It works. A profiler, a linter, or a blog post then suggests the possessive form, because "the `+` never needs to give anything back here":

```text
^[\w.]++\.com$
```

It does need to give something back. `[\w.]` includes the dot, so the possessive run swallows `.com` as well, and `\.com` is left with an empty string and no way to reclaim what was taken. The pattern still compiles. Tests that only check rejected input still pass. **Every valid hostname now fails**, and the diff that caused it is two characters long.

The rule that predicts this is short: **a possessive quantifier over a class that overlaps what follows it is a bug.** `[\w.]++` followed by `\.` overlaps. `\d++` followed by `\.` does not, because `\d` can never match a dot — which is why `\d++\.\d+` is the canonical *good* use and appears in every tutorial.

## Where they genuinely pay

The other direction is worth the trouble. `^(a+)+$` against a long run of `a`s and one `!` is the classic exponential search: the nested quantifiers can split the run in exponentially many ways, and a subject that cannot match forces the engine to try all of them.

No timings appear below, because a timing is not reproducible. Each question is asked in a **child process with a hard five-second cap**, and the recorded answer is one of three words — the two subject sizes sit far enough either side of the cliff that every machine agrees which cell says what.

<!-- output:atomic_cliff_py -->
*Verified output of [`atomic_cliff_py.py`](examples/atomic_cliff_py.py) — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
subject: n copies of 'a' and then '!', which nothing here can match --
the engine has to PROVE it, and that is the expensive direction.
pattern      n=16             n=40
^(a+)+$      no match         no answer in 5s
^(?>a+)+$    no match         no match
^(a++)+$     no match         no match

subject: n copies of 'a' and nothing else -- all three still match it,
so cutting the backtracking did not cost a single true answer.
pattern      n=16             n=40
^(a+)+$      match            match
^(?>a+)+$    match            match
^(a++)+$     match            match
```
<!-- /output -->

Sixteen `a`s is a few thousand steps. Forty is 2⁴⁰ — more than a day on any hardware, which is why that cell says nothing came back. One `?>` or one `+` removes the entire search space, and the second table is the point worth insisting on: **the fix did not cost a single true answer**. Everything that matched before still matches.

That is the honest summary of when to reach for these: when the quantifier is genuinely deterministic — when what follows it cannot be matched by it — you get the same results and a bounded search. When it is not, you get different results.

Four things to take from that table.

**Perl, Ruby, Java and Python all agree**, down to the hostname bug. This is a construct with genuinely uniform semantics across the engines that have it — rarer than it sounds in this library.

**JavaScript has neither, at any version.** Not `(?>…)`, not `++`, not `*+`, not `?+`. The last two rows of the probe are the workaround, which JavaScript answers exactly like the four engines that have the real feature.

**Python's row is a 3.11 story**, and it is the reason this page exists in a library rather than in your memory of the language. The probe above runs one interpreter; six of them, on one machine, split cleanly:

**The last two rows are the same emulation** every engine can run, and they are the subject of the next section.

## JavaScript: the trick that builds one out of two other features

```text
(?=(a+))\1
```

A lookahead that captures, followed by a backreference that re-consumes what it captured. It works because **a lookahead is not re-entered after it succeeds**: the engine runs `a+` greedily inside the assertion, records the longest run in group 1, and then never goes back to try a shorter one. `\1` then puts that exact text on the consuming path. The saved positions are gone — which is the whole definition of an atomic group.

<!-- output:atomic_emulation_js -->
*Verified output of [`atomic_emulation_js.js`](examples/atomic_emulation_js.js) — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
(?>a+)b  SyntaxError
a++b     SyntaxError
a*+b     SyntaxError
a?+b     SyntaxError
a+a                    on "aa"           -> "aa"
(?=(a+))\1a            on "aa"           -> no match
(?=(a+))\1b            on "aab"          -> "aab"
^[\w.]+\.com$          on "example.com"  -> "example.com"
^(?=([\w.]+))\1\.com$  on "example.com"  -> no match
emulated atomic on 30 a's and a '!': false
emulated atomic on 30 a's: true
```
<!-- /output -->

The four `SyntaxError` lines are all four spellings being refused. Then `(?=(a+))\1a` fails on `"aa"` exactly as `a++a` does everywhere else, `(?=(a+))\1b` still matches `"aab"`, and — the proof that this is not a toy — the hostname pattern reproduces the *bug* faithfully too. An emulation that copied only the good half would not be an emulation.

The last two lines are the payoff: `^(?:(?=(a+))\1)+$` answers on thirty `a`s and a `!` immediately, where `^(a+)+$` on the same subject needs about 2³⁰ attempts.

The same trick works in every engine with lookahead and backreferences — the Python run above uses it too, and the probe's last two rows show Perl, Ruby and Java agreeing. Reach for it when you need atomic behaviour in JavaScript, or in any pattern that has to run in both JavaScript and a Perl-family engine. The costs are real but small: one extra capture group, which renumbers every group after it, and a pattern that no longer reads like what it does. Leave a comment.

## Rust, where the two crates disagree — and one of them surprised this page

<!-- output:atomic_rs_sh -->
*Verified output of [`atomic_rs_sh.sh`](examples/atomic_rs_sh.sh) — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
regex:       (?>a+)b        refused --
regex parse error:
    (?>a+)b
      ^
error: unrecognized flag
regex:       a++a           on aa   -> true
regex:       a++b           on aab  -> true
fancy-regex: (?>a+)b        on aab  -> Ok(true)
fancy-regex: (?>a+)a        on aa   -> Ok(false)
fancy-regex: a++b           on aab  -> Ok(true)
fancy-regex: a++a           on aa   -> Ok(false)
fancy-regex: ^[\w.]++\.com$ on example.com -> Ok(false)
```
<!-- /output -->

`fancy-regex` is the backtracker, and it implements both constructs properly: `(?>a+)a` and `a++a` fail, `(?>a+)b` and `a++b` match, the hostname pattern reproduces the bug. If you are porting Perl patterns to Rust, this is the crate that will agree with the original.

The `regex` crate is the finite automaton, and this is where a run overturned an expectation. `(?>a+)b` is refused — and the error is worth reading, because it is not "atomic groups are unsupported". The parser sees `(?` and expects inline flags, so `>` is reported as an *unrecognised flag*. The construct is not merely absent; the syntax is not reserved.

**`a++a` compiles — and matches `"aa"`.** It is parsed as a repetition of a repetition, `(a+)+`, so the inner `+` hands a character back exactly as it always did. There is no possessive quantifier in `regex`; there is a pattern that looks like one and means the opposite. That is the most dangerous kind of difference — no error, no warning, a silently different answer. The automaton is not slower for it, because it never backtracks in the first place.

Go's `regexp`, which is the same family and the same guarantee, made the opposite call. Both spellings are rejected, by name:

*Real run — Go 1.25.5 darwin/amd64, macOS 26.6.2 x86-64, 2026-09-22.*

```console
$ go run main.go
(?>a+)b  refused: error parsing regexp: invalid or unsupported Perl syntax: `(?>`
a++b     refused: error parsing regexp: invalid nested repetition operator: `++`
a*+b     refused: error parsing regexp: invalid nested repetition operator: `*+`
```

If you are choosing between the two automaton engines and you paste patterns from Perl, that difference matters more than it looks.

## PCRE2, so ABAP

ABAP's `PCRE` addition (7.55 and later) is the PCRE2 library in the kernel, so the answer is Perl's answer. PCRE2 is on any machine with `pcre2grep`:

*Real run — PCRE2 10.48 (`pcre2grep`), macOS 26.6.2 x86-64, 2026-09-22. The subject file holds `aab` on line 1 and `example.com` on line 2.*

```console
$ pcre2grep '(?>a+)b' subject.txt
aab
$ pcre2grep 'a++b' subject.txt
aab
$ pcre2grep 'a++a' subject.txt
$ pcre2grep '^[\w.]+\.com$' subject.txt
example.com
$ pcre2grep '^[\w.]++\.com$' subject.txt
```

The two commands that print nothing exit with status 1: no line matched. `a++a` matched neither line, and the possessive hostname pattern matched neither line — the same two results as Perl, Python, Ruby and Java above.

In ABAP source the construct goes inside the pattern literal like any other, and the failure mode is the quiet one: a `FIND` that matches nothing sets `sy-subrc = 4` and dumps nothing.

## When not to reach for them

1. **When the quantified thing overlaps what follows it.** `[\w.]++\.com`, `.*+;`, `[a-z]++e` — each one matches nothing, forever. If you cannot say out loud why the next element can never be matched by the quantifier, do not make it possessive.
2. **As a blanket optimisation.** Sprinkling `+` after every quantifier is not a speedup pass; it is a semantics change with a speedup sometimes attached. Change one quantifier, run the tests, keep the diff small enough to revert.
3. **When the pattern has to run in JavaScript too.** Use the lookahead emulation in both places rather than maintaining two patterns that differ by two characters.
4. **When the real problem is the pattern's shape.** `^(a+)+$` does not need an atomic group; it needs to not be `^(a+)+$`. Removing a nested quantifier or making two alternatives mutually exclusive fixes the search *and* leaves a pattern the next reader can follow.
5. **When you are on an engine that cannot explode.** In Go's `regexp` and Rust's `regex` there is no backtracking to suppress, so the only thing a possessive quantifier can do there is confuse — or, in `regex`, quietly mean something else.

The place they are unambiguously right: a long, deterministic run — digits, hex, whitespace, a quoted string's contents — inside a pattern that will often *fail*. `\d++\.\d+`, `"[^"]*+"`, `\s*+\S`. Those are the cases where the saved backtracking positions were never going to be used, and keeping them is pure cost.
